Cheat sheet · for your projects

Most of what users call “the AI” is the system you build around the model.

Ask on every project

  1. Which ring is this really: hand-written rules, classic ML or a generative model?
  2. What exactly is sent to the model on each call, and who decides that?
  3. Where do facts the model can’t know come from: private data, recent events?
  4. Which actions can it take, and who or what approves them before they run?
  5. How will we know it got worse after a model, prompt or data change?

Rules of thumb

  • Name the box before you fix anything: model, context, knowledge, tools or another.
  • Rule out context, knowledge and tools before you blame the model.
  • Use a plain rule instead of a model when a fixed rule does the job reliably.
  • Judge quality on a set of test cases you can rerun, not on one good demo.
Checklist

System map in five minutes

  • Pick one real user request and trace it from the interface to the answer, step by step.
  • Mark the model call. Every other step belongs to the system.
  • Sort each step into the eight boxes; one step can touch two boxes.
  • For each empty box, ask: missing by design, or missing by accident?
  • Note what each box adds per request in cost and delay.
  • Circle the box most likely to fail first, and name who owns it.

Leave at the door

Five myths this module breaks.

MythWhat’s actually true
“The model learns from my chats.”Weights don’t change during inference.
“It looks things up to answer.”Only if the system gives it a search tool.
“Better prompts are the main lever.”Context, data and tools usually matter more.
“The demo worked, so it works.”A demo is one sample, not an evaluation.
“The AI decided.”Someone configured that behavior.
